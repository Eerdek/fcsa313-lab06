## 1. Ажлын орчин ба PICT-ийг эх кодоос бүтээсэн нь

Миний машин: Windows 11 Pro (26200). Энд **Smart App Control** enforcement горимд

Гарын үсэггүй exe-г "An Application Control policy has blocked this file" гэж хаадаг. Энэ хоригт
pip-ээр суулгасан `cmake.exe`, `zig.exe` хаагдсан бөгөөд эх кодоос бүтээсэн `pict.exe` ч мөн ажиллахгүй.
WSL ч суугаагүй.

Тиймээс PICT-ийг лабын заасан **Ubuntu** орчинд, зааварт бичсэн командуудаар эх кодоос нь бүтээсэн.
Бүтээлтийг GitHub Actions-ийн `ubuntu-24.04` runner дээр
[`.github/workflows/pict.yml`](.github/workflows/pict.yml) хийдэг:

```bash
sudo apt-get install -y git cmake g++ make
mkdir -p ~/tools && cd ~/tools && git clone https://github.com/microsoft/pict && cd pict   # репоноос ГАДНА
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j4
sudo cp build/cli/pict /usr/local/bin/
(git -C ~/tools/pict log -1 --format='pict commit %h %ad' --date=short; pict 2>&1 | head -3) | tee results/pict-build.txt
```

- PICT-ийн эх код, `build/` нь runner-ийн `~/tools/pict`-д үлдэх тул энэ репод ордоггүй.
  `.gitignore`-д `pict/` ба `build/`-ийг мөн нэмсэн.
- PICT-ийг `ab76c25` commit дээр тогтоосон тул дахин ажиллуулах бүрт ижил гаралт гарна.
- Workflow нь репо дахь бүх `*.model`-ийг ажиллуулж `results/*.txt`-ийг дахин үүсгэдэг.
  Дараа нь commit хийгдсэн `results/`-тэй `git diff --exit-code`-ээр тулгадаг. Ингэснээр README ба
  `results/`-ийн тоо PICT-ийн бодит гаралттай таарч байгааг push бүрд шалгана.
- `results/*.txt` файлуудыг workflow-ийн artifact-аас татаж аваад өөрөө commit хийсэн.

## 2. Хэсэг A — Category-Partition гараар: `POST /transfer`

**Тестийн бэхэлгээ (setup), бүх хүснэгтэд нийтлэг:**
- from данс `ACC-100`, валют **MNT**;
- өдрийн лимит **L = 1 000 000 MNT**;
- ханш **1 USD = 3 400 MNT**.

Тэмдэглэгээ: **x** = хөрвүүлсний дараах дүн (MNT), **B** = from-ийн үлдэгдэл, **R** = өнөөдөр үлдсэн лимит (L − өнөөдөр шилжүүлсэн).

### A1 — Сонголтууд ба төлөөлөх утгууд

| Параметр | Сонголт (category) | Утга | Төлөөлөх утга / setup | Хязгаарлалт (A2) |

**Далд орчны сонголт:** Хүсэлтийн body-д харагдахгүй ч үр дүнг тодорхойлдог 3 зүйл бий:
1. **өдрийн лимитээс аль хэдийн хэр ашигласан** (L1–L3). Ижил amount=400 000 нь L1 үед OK, L2 үед
   яг лимит, L3 үед ERROR_LIMIT болно.
2. **from-ийн үлдэгдэл B.** M4/M5-ийн setup-аар тогтоосон.
3. **ханш.** C2-ийн setup-аар тогтмол 3 400 болгосон. Ханш өөрчлөгдөхөд хил хаашаа шилжихийг
   тодорхойлолт хэлдэггүй.

### A2 — Хязгаарлалтууд ба үндэслэл

- **[ERROR]** — F2, F3, T2, T3, M2, M3, M5, M7, L3. Тус бүр тодорхойлолтод заасан нэг ERROR_ код
  буцаах ёстой. Нэг алдаа бусдыгаа нуудаг (error masking) тул бусад сонголттой хослуулах нь тест
  нэмэхгүй. Тиймээс тус бүрийг **ганц удаа** шалгана.
- **[SINGLE]**:
  - **M4, M6** нь "хэтрэхгүй" (≤) гэсэн хилийн утга. Тэнцүү үед зөвшөөрөгдөх эсэхийг нэг тест л
    тогтооно, бусадтай хослуулах шаардлагагүй.
  - **T4** (to царцаагдсан) нь тодорхойлолтод **огт дурдагдаагүй**. Шууд утгаар уншвал 201 OK байх ёстой
    тул нэг удаа шалгаж, шаардлагын эзэнтэй тодруулах асуулт болгоно.
- **[property hasAccount] / [if hasAccount]** — Байхгүй from данс (F3)-д үлдэгдэл, лимит, валют
  байхгүй тул B, R, "Different" гэсэн ойлголт **утгагүй**. Мөн "to = from" нь байхгүй данстай адил болно.
  Тиймээс M4–M7, C2, T3, L1–L3 зөвхөн from данс байгаа үед утгатай.
- **[property hasRemaining] / [if hasRemaining]** — L3 (R = 0) үед "0 < x < R" (M1),
  "x = B < R" (M4), "x = R" (M6) **гаргах боломжгүй**: R = 0 бол x = 0 нь Zero болно.
- **[property converted]** — C2 нь хөрвүүлэлтийн замыг идэвхжүүлнэ. Хөрвүүлсний дараах дүнгээр
  B/R-ийг давах сонирхолтой тохиолдлыг A3-ын S19 мөрөнд тусад нь гаргасан.

**Тоо (Лекц 6-ын find жишээний маягаар):**

```
Бүрэн олонлог : 3 (from) × 4 (to) × 7 (amount) × 2 (currency) × 3 (limit used) = 504
Хязгаарлалтын дараа:
  [ERROR]  : F2, F3, T2, T3, M2, M3, M5, M7, L3            = 9 frame (тус бүр 1)
  [SINGLE] : T4, M4, M6                                     = 3 frame (тус бүр 1)
  Хэвийн   : F1 × T1 × M1 × {C1, C2} × {L1, L2} = 1·1·1·2·2 = 4 frame
  Нийт     : 9 + 3 + 4                                       = 16
=> 504 → 16
```

### A3 — Спецификацийн хүснэгт

**Олон алдааны давуу эрэмбэ (миний тогтоосон):**
`NO_FROM → FROZEN → NO_TO → SAME_ACCOUNT → BAD_AMOUNT → INSUFFICIENT → LIMIT`.

**Үндэслэл:** Шалгалт бүр өмнөхөө давсан байхыг шаарддаг. Хамаарлын дарааллаар:
- B ба R-тэй харьцуулахын тулд from данс байгаа, идэвхтэй, дүн нь хүчинтэй байх ёстой;
- "to = from" шалгалт хоёр данс хоёулаа олдсоныг шаарддаг;
- илгээгчийн асуудлыг хүлээн авагчийнхаас өмнө шалгана;
- бодит үлдэгдэл (INSUFFICIENT) нь бодлогын лимитээс (LIMIT) өмнө.

## 3. Хэсэг B — PICT: pairwise covering array

### B1 — Лекцийн браузерын жишээ (`browser.model`)

```
Content:   Allow, Restrict, Block
Cookies:   Allow, Restrict, Block
Popups:    Yes, No
Addons:    Yes, No
Attacks:   Yes, No
Forgeries: Yes, No
```

| Ажиллуулсан | Файл | Мөр (толгойг хассан, `tail -n +2 \| wc -l`) |
|---|---|---|
| `pict browser.model` (2-way) | `results/browser-2way.txt` | **10** |
| `pict browser.model /o:3` (3-way) | `results/browser-3way.txt` | **20** |
| Бүрэн олонлог 3·3·2·2·2·2 | — | 144 |

`/r` (санамсаргүй seed) ашиглаагүй тул ижил моделиос үргэлж ижил гаралт гарна. CI push бүрд үүнийг
дахин үүсгэж commit хийсэн файлтай тулгадаг.

- **2-way: PICT 10 мөр өгсөн, лекц дээр гараар 9-д багтаасан.** 9 бол онолын доод хязгаар:
  Content × Cookies хоёр 3 утгатай тул тэдний 3·3 = 9 хос бүр дор хаяж нэг мөр шаардана. PICT-ийн
  алгоритм **greedy**: мөр бүрийг "одоогоор хамрагдаагүй хамгийн олон хосыг хамрах" зарчмаар нэг
  нэгээр нь сонгодог бөгөөд эргэж буцаж оновчлохгүй. Тиймээс ихэнх тохиолдолд оновчтойд ойр
  (энд +1 мөр) гаргадаг ч хамгийн цөөнийг **заавал** өгдөггүй.
- **3-way: 20 мөр.** Гурвалын доод хязгаар 3·3·2 = 18 (Content × Cookies × хоёр утгатай нэг
  параметр). Бүрэн олонлог 144-тэй харьцуулбал **144 → 20 (≈ 86% бага)** мөрөөр бүх гурвалыг
  хамарна. 2-way-аас 2 дахин олон боловч бүрэн олонлогийн ердөө 14%.

### B2 — Шилжүүлгийн модель PICT-ээр

Хэсэг A-гийн сонголтуудыг PICT рүү ингэж буулгасан:
- **From, To, Currency** — A-гийнхтай ижил.
- **Amount** — x-ийг B ба R-тэй харьцуулсан 7 утга.
- **LimitUsed** — далд орчин, `None` / `Partial`. A-гийн L3 "Full" (R = 0) үед ямар ч эерэг дүн
  `OverLimit` болох тул тусад нь утга болгоогүй.
- **To = Frozen** нь [ERROR] биш, [SINGLE] учир хэвийн утга хэвээр.

| Файл | Хязгаарлалт |
|---|---|
| [`transfer-nc.model`](transfer-nc.model) | байхгүй |
| [`transfer.model`](transfer.model) | A2-ын `[if hasAccount]`: `IF [From] = "Missing" THEN [To] <> "SameAsFrom" AND [Amount] IN {"Normal","Zero","Negative"} AND [Currency] = "Same" AND [LimitUsed] = "None";` |
| [`transfer-neg.model`](transfer-neg.model) | [ERROR] утгууд `~`-тэй + дээрх IF хэвээр |

Мөр бүрийн алдааны тоог A2-ын [ERROR] утгуудаар тоолсон: From Frozen/Missing, To Missing/SameAsFrom,
Amount Zero/Negative/OverBalance/OverLimit.

| Хувилбар | Файл | Мөр | 0 алдаатай мөр | Жинхэнэ happy path (From=Valid, To=Valid, Amount=Normal) | Мөр дэх алдаа: 0 / 1 / 2 / 3 | Нэг мөр дэх хамгийн их алдаа |
|---|---|---|---|---|---|---|
| Хязгаарлалтгүй | `results/transfer-nc.txt` | **28** | 4 | **0** | 4 / 4 / 15 / 5 | 3 |
| A2 хязгаарлалттай | `results/transfer.txt` | **30** | 3 | **1** (мөр 18) | 3 / 10 / 14 / 3 | 3 |
| `~` сөрөг утгатай | `results/transfer-neg.txt` | **27** | 6 | **1** (мөр 5) | 6 / 21 / 0 / 0 | **1** |

**Ажиглалт:**
- **Happy path гарсан уу?**
  - Хязгаарлалтгүй 28 мөрөнд Valid/Valid/Normal мөр **нэг ч алга**. Бүх хос хамрагдсан ч "бүгд хүчинтэй"
    гэсэн нэг мөр pairwise-ийн шаардлага биш. 0 алдаатай 4 мөр нь бүгд хил (EqualBalance/EqualLimit)
    эсвэл To=Frozen-той.
  - Хязгаарлалт нэмэхэд санамсаргүйгээр 1 happy мөр гарсан.
- **Нэг мөрөнд хэдэн алдаа?**
  - transfer-nc-ийн 28 мөрийн **20** нь 2–3 алдаатай. Жишээ нь мөр 16 `Frozen | Missing | OverBalance` нь
    гурван алдаатай. Эрэмбээр зөвхөн ERROR_FROZEN буцах ба NO_TO, INSUFFICIENT шалгалтууд **нуугдана**
    (error masking).
  - Ийм мөр юуг шалгаж байгаа нь тодорхойгүй. Хариу нь зөвхөн бидний тогтоосон давуу эрэмбээс
    хамаарна. Тиймээс тэр эрэмбийг баталгаажуулахаас өөр зүйл шалгахгүй.
- **Хязгаарлалт мөрийн тоог багасгаагүй, эсрэгээр 28 → 30 болгосон.** IF нь From=Missing-ийн хосуудыг
  хорьсон тул Missing-ийн хамрах ёстой хосуудыг (Missing × Frozen-To, Missing × Zero гэх мэт) цөөн
  мөрөнд шахах боломж буурсан. Greedy алгоритм нэмэлт мөрөөр нөхсөн. Хамгийн чухал нь
  **transfer-nc-ийн From=Missing 10 мөрийн 9 нь (мөр 2, 4, 10, 11, 14, 15, 23, 26, 28) бодитоор
  байгуулах боломжгүй** байсан. Эдгээр нь байхгүй данстай Equal/OverBalance/Limit, Different, Partial
  эсвэл to = from хослол юм. transfer.txt-ийн From=Missing 4 мөр (17, 28, 29, 30) бүгд байгуулах
  боломжтой.
- **`~`-ийн нөлөө:** 27 мөр, мөр бүрт **хамгийн ихдээ 1 алдаа**. 6 мөр 0 алдаатай хэвийн/хилийн
  комбинаци, 21 мөр яг нэг алдаатай. 8 [ERROR] утга бүр 2–5 удаа, өөр өөр хэвийн утгуудтай гарсан.
  Энэ нь category-partition-ий [ERROR] "ганц удаа, бусдыг нь хэвийн" санаатай дүйцнэ.
  Oracle нь давуу эрэмбээс хамаарахаа больсон.
- **`~` хэрэглэхэд A2-ын IF хэрэгтэй хэвээр үү? — Тийм.** `~` нь "нэг мөрөнд нэгээс олон сөрөг утга
  байхгүй" гэдгийг л баталгаажуулна. From=Missing (сөрөг) мөрөнд Amount-ийн **хэвийн** утгууд болох
  EqualBalance, EqualLimit-ийг оруулах боломжтой хэвээр. Харин тэдгээр нь байхгүй дансанд B, R
  байхгүй тул **байгуулах боломжгүй**. IF-ийн ачаар transfer-neg-ийн From=Missing хоёр мөр
  (14, 27) зөвхөн `Normal | Same | None`-той гарсан. `~` нь error masking-ийг шийддэг, IF нь
  боломжгүй хослолыг шийддэг. Хоёр өөр асуудал юм.

#### PICT гаралтаас бодит тест кейс (Лаб 5-ын хэв маяг)

Нийтлэг setup:
- `ACC-100` (MNT, идэвхтэй);
- `ACC-300` (MNT, идэвхтэй);
- `ACC-200` (царцаагдсан, үлдэгдэл 200 000);
- `ACC-400` (царцаагдсан to данс);
- `ACC-998` нь байхгүй;
- өдрийн лимит L = 1 000 000 MNT, ханш 1 USD = 3 400 MNT.

### B3 — Гараар (A3) ба PICT-ийн гаралтын харьцуулалт

| Шалгуур | Гараар — A3 (19 спец) | PICT — transfer-neg (27 мөр) |
|---|---|---|
| **Алдааны семантик** | **Илүү сайн.** Мөр бүр зорилготой: ERROR тус бүр ганц удаа хэвийн орчинд, давхар нөхцөл (S17, S18) нь давуу эрэмбийг зориуд шалгадаг. Хөрвүүлсний дараах хил (S19) гэх мэт **утгын түвшний** сонирхолтой тохиолдол бий | Утгын нэрээр л хослуулдаг. "100 USD < B боловч 340 000 > B" гэх мэт тоон утгын нарийн тохиолдлыг өөрөө үүсгэдэггүй. `~`-гүй бол (transfer-nc) 28-аас 20 мөр нь олон алдаатай |
| **Хосын хамралт** | **Баталгаагүй.** 16 frame нь [ERROR]/[SINGLE]-ийг ганц удаа авдаг тул, жишээ нь To=Frozen × Currency=Different, EqualBalance × Partial, EqualLimit × Different зэрэг хосууд хамрагдаагүй | **Баталгаатай.** Бүх утгын хос (сөрөг утгыг ч гэсэн хэвийн утгуудтай) дор хаяж нэг удаа гарна. Хүний мартах хослолыг ч механикаар хамарна |
| **Happy path** | S1–S4 зориуд оруулсан | transfer-nc-д огт гараагүй, transfer/neg-д санамсаргүйгээр 1 мөр |

Хоёр аргыг хамт ашиглах нь зөв. Category-partition нь утга, хязгаарлалт, oracle-ийг тодорхойлдог.
PICT нь тэр утгуудын хосуудыг **механикаар бүрэн хамарсан** цөөн мөр гаргадаг. Сонирхолтой тоон хилийг
(S19 гэх мэт) гараар нэмнэ.

## 4. Дүгнэлт

1. Category-partition нь тодорхойлолтыг сонголт, утгад задалж, [ERROR]/[SINGLE]/[IF]-ээр 504 хослолыг 16
   утга учиртай frame болгосон.
2. Хамгийн их бодол шаардсан алхам бол **amount-ийн сонголт** байсан. Дүнг хөрвүүлсний дараа үлдэгдэл ба
   **үлдсэн** лимиттэй харьцуулах ёстой гэдгээс далд орчны сонголт (өнөөдөр хэр зарцуулсан) гарч ирсэн.
3. Хоёрдугаарт тодорхойлолт чимээгүй **олон алдааны давуу эрэмбийг** тогтоох байсан. Энэ эрэмбэ A3-ын
   давхар нөхцөл болон PICT-ийн олон алдаатай мөрийн oracle-ийг шууд тодорхойлсон.
4. PICT хосын хамралтыг механикаар баталгаажуулдаг: 144 хослолыг 2-way-д 10, 3-way-д 20 мөрөөр хамарсан.
5. Гэхдээ greedy тул оновчтойг заавал өгдөггүй (лекцийн 9-ийн оронд 10), хязгаарлалт нэмэхэд мөр 28 → 30
   болж өссөн.
6. Хязгаарлалтгүй модель байгуулах боломжгүй 9 мөр, олон алдаатай 20 мөр гаргаж, жинхэнэ happy path
   мөр огт гаргаагүй. Модель муу бол хамралт ч ач холбогдолгүй.
7. `~` нь [ERROR]-тэй дүйцэж мөр бүрт ганц алдаа гаргасан ч боломжгүй хослолыг шийдэхэд IF хэрэгтэй хэвээр.
8. Гараар хийсэн задаргаа **алдааны семантикийг**, PICT **хосын хамралтыг** илүү сайн барьдаг тул эхлээд
   category-partition-оор модель гаргаж, дараа нь PICT-д өгөх, тоон хилийг гараар нэмэх нь хамгийн үр дүнтэй.
9. Кодгүйгээр тодорхойлолт дээр ажилласнаар (shift-left) to данс царцаагдсан, олон алдааны эрэмбэ зэрэг
   шаардлагын цоорхой код бичихээс өмнө илэрсэн.

## 5. Нэмэлт даалгавар — AI-ийн модельтой харьцуулах

AI туслахад зөвхөн шилжүүлгийн тодорхойлолтыг өгч "category-partition аргаар сонголт, утга, хязгаарлалт
гаргаад PICT модель бич" гэж хүссэн. Миний хариултыг AI-д үзүүлээгүй.
- AI-ийн хариулт: [`ai/ai-answer.md`](ai/ai-answer.md), засваргүй;
- AI-ийн модель: [`ai/ai-transfer.model`](ai/ai-transfer.model), CI-д ажиллуулсан;
- гаралт: `results/ai-transfer.txt` (**32 мөр**).

1. **AI юу мартав, юу илүү санав:**
   - Мартсан: **to данс царцаагдсан** тохиолдол (тодорхойлолт чимээгүй [SINGLE]), from данс
     байхгүй үеийн боломжгүй хослол.
   - Илүү санасан: ханшийн **чиглэл**ийг (`Rate: GreaterThanOne / LessThanOne`), бутархай/0.01-ийн
     нарийвчлал, үл мэдэгдэх валютын код зэрэг тодорхойлолтын цоорхойг.
   - AI мөн үлдэгдэл, лимитийг тусдаа параметр болгосон нь миний нэг Amount параметрээс уян хатан.
2. **Хязгаарлалт хэтэрсэн үү? — Тийм, нэг газар.** `IF [Balance] = "Equal" THEN ... [Currency] = "Same"`
   ба Limit-ийн адил дүрэм нь хилийн утгыг хөрвүүлэлттэй хослуулахыг **бүрэн хориглосон**.
   Гаралтад Equal × Different мөр **0**. Гэтэл "хөрвүүлсний дараа яг үлдэгдэлтэй тэнцэх" нь
   бөөрөнхийлөлтийн алдаа гарах магадлалтай, тестлэх ёстой хослол.
3. **Дутуу хязгаарлалт:** From=`~Missing` мөрийг үлдэгдэл/лимит/валюттай хослохыг хориглоогүй тул
   32 мөрийн **4 нь** (10, 12, 31, 32: байхгүй данстай `Equal` эсвэл `Different`) бодитоор
   байгуулах боломжгүй.
4. **Мөрийн тоо:** AI 32 мөр, 0 алдаатай 4 мөр, мөр бүрт хамгийн ихдээ 1 алдаа (`~` зөв ашигласан).
   Миний transfer-neg 27 мөр, 0 алдаатай 6 мөр. AI-ийн модель 7 параметр (Rate нэмэлт)-тай тул мөр
   олон гарсан. Харин боломжгүй мөр гаргасан бөгөөд хөрвүүлэлтийн хилийг алгассан.
5. **Дүгнэлт:** AI хурдан, тодорхойлолтын цоорхойг сайн жагсаасан. Гэхдээ хязгаарлалт нь хоёр чиглэлд
   алдаатай байлаа: хэт хатуу (Equal × Different хасагдсан) ба хэт сул (Missing × Equal зөвшөөрөгдсөн).
   Тиймээс AI-ийн моделийг PICT-ээр ажиллуулж гаралтыг мөр мөрөөр шалгахгүйгээр итгэх аргагүй.
